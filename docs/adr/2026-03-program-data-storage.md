# ADR: Define User-Scoped Storage Locations

- Status: Proposed
- Date: 2026-03-14
- Deciders: Ipponboard maintainers

## Context

Ipponboard needs a clear contract for where the application reads shipped assets from and where it stores writable user data. Without that contract, runtime code, installers, support documentation, and packaging work will drift apart.

The application does not require administrative privileges and is intended to be installed in the user's context rather than in the system context. The storage model should therefore follow established user-scoped application conventions on each platform.

Ipponboard is a Qt application and should use Qt's cross-platform abstractions wherever practical instead of hard-coded platform-specific writable paths.

The main requirement is to keep three path categories clearly separated:

1. the program directory, which contains shipped program assets and is treated as read-only at runtime
2. the local application data directory, which contains logs and other local runtime or generated data
3. the user configuration directory, which contains user-configured persistent data

## Decision

Adopt a user-scoped storage model built around three application paths.

### The Three Paths

#### 1. Program Directory

Purpose:

- contains shipped program assets
- treated as read-only at runtime

Rules:

- the application must never write into the program directory
- immutable built-in assets should preferably be embedded in Qt resources and accessed through `:/...`
- if an asset is still packaged as a file, it is still program-owned and read-only
- `QCoreApplication::applicationDirPath()` may be used only to locate packaged read-only files that are not embedded in Qt resources

Examples:

- bundled manuals
- bundled license files
- bundled translation files
- other read-only shipped assets

#### 2. Local Application Data

Purpose:

- contains local runtime data generated by the application
- used for writable data that is not user configuration

Qt mapping:

- `QStandardPaths::AppLocalDataLocation`

Rules:

- use this path for logs, exports, autosaves, generated files, caches, and similar local data
- this location is writable and survives normal application updates
- this data is local to the current machine and should not be treated as configuration

Examples:

- log files
- autosave files
- exported documents
- generated working files

#### 3. User Configuration Directory

Purpose:

- contains persistent user-configured data
- used for settings and editable configuration owned by the user

Qt mapping:

- `QSettings` for application settings
- `QStandardPaths::AppConfigLocation` for user configuration files

Rules:

- use this path for configuration the user or application treats as persistent settings
- if a shipped default must become editable, copy it here before modification when it is configuration data
- user configuration must not be written back into packaged read-only assets

Examples:

- user-editable configuration files
- persistent application settings
- customized configuration derived from shipped defaults

### Cross-Platform Rules

The following rules apply on all supported platforms:

1. Ipponboard is installed in the user's context. Runtime code must not assume a system-wide installation.
2. Writable application paths must be resolved through Qt abstractions, not through hard-coded platform-specific paths.
3. Program-owned assets are always read-only at runtime.
4. Logs and other local runtime-generated data belong in `QStandardPaths::AppLocalDataLocation`.
5. User-configured persistent data belongs in `QStandardPaths::AppConfigLocation` or in `QSettings`, depending on whether it is file-based configuration or application settings.
6. If a shipped default must become editable, the application must treat the shipped copy as a read-only seed and copy it to a writable Qt-managed location before modification.
7. The application must never write back into installed assets, the application bundle, or other packaged program-owned locations.

### Platform Mapping

The runtime code should use Qt APIs, but the expected platform behavior is:

- **Windows**
  - _program directory_: user-scoped installed program files
  - _local application data_: `QStandardPaths::AppLocalDataLocation`, typically under `%LOCALAPPDATA%`
  - _user configuration_: `QStandardPaths::AppConfigLocation`, typically under `%APPDATA%`

- **Linux**
  - _program directory_: installed program files in the packaging-defined location
  - _local application data_: `QStandardPaths::AppLocalDataLocation`, typically under `$XDG_DATA_HOME` or `~/.local/share`
  - _user configuration_: `QStandardPaths::AppConfigLocation`, typically under `$XDG_CONFIG_HOME` or `~/.config`

- **macOS**
  - _program directory_: the installed application bundle, treated as read-only at runtime
  - _local application data_: `QStandardPaths::AppLocalDataLocation`, in the user-specific application data location selected by Qt
  - _user configuration_: `QStandardPaths::AppConfigLocation`, in the user-specific configuration location selected by Qt

## Consequences

### Positive

- Gives contributors a simple three-path model to follow.
- Aligns with Qt's standard cross-platform approach for writable application storage.
- Keeps runtime-generated data separate from user configuration.
- Prevents accidental writes into packaged program assets.
- Supports a per-user installation model without requiring administrative privileges.

### Negative/Risks

- Existing code that reads or writes beside the executable must be updated carefully.
- `QStandardPaths::AppLocalDataLocation` and `QStandardPaths::AppConfigLocation` must be used consistently so data does not drift into ad hoc locations.
- Resource-based or bundled defaults require explicit copy-out behavior before user modification.

## Rollback Strategy

If the chosen layout causes regressions:

1. Detect legacy paths before writing new data.
2. Read from the new Qt-resolved location first and fall back to the legacy location during the rollback window.
3. Stop relocating files to the new layout and document the temporary rollback in release notes.

Once stability is restored, the storage model can be revisited with updated requirements.
